# ROADMAP

What we know is not finished, why it matters, how well it is evidenced, and the next step. Labels: **[measured]** we ran it and kept the log, **[read]** taken from code or a document, **[guess]** not verified. Test machine: GTX 1050 Ti 4 GB, 16 GB RAM. Contributions welcome: see `CONTRIBUTING.md`.

| What | Why | Evidence now | Next step |
|---|---|---|---|
| Longer single-pass research | Longer single clips without seams | Not part of this release; no measurement beyond 209 frames [not tried] | Open research question; any new length needs its own measurements and gates first |
| Direct byte reference for 158 to 209 frames | Today byte evidence exists only for 56 frames and the 141-frame latent; longer clips rely on the gate chain | Gate chain passed [measured]; the unpatched build cannot run these lengths on this card [measured] | Run the same recipe on a larger-memory machine or the CPU path to obtain a reference, then compare hashes |
| Speed | 209 frames take about 45 min of sampling plus 3 min of VAE | Sampling about 2730 s and VAE about 173 s with the release binary, 3414 s in total [measured: U209; older development runs 2664 s and 174 s] | Overlap weight loading with compute, fewer copies per block, check the NVMe read path; quality settings stay fixed |
| Speed-pack profiles on other cards | The optional profiles (`uret.ps1 -Profil`) were measured on one 4 GB card; the 832x480 x 141 cell has single-digit MB of headroom | One card, two prompts per cell [measured]; long-prompt cases only gate-read [measured, partial]; 260 frames conditional [measured] | Reports from other 4 GB cards and longer prompts; an end-to-end 260-frame run through `uret.ps1` with the early exit; a direct flag-off reference where it fits |
| Other cards and drivers | Only one GPU was tested by us | One card [measured]; first outside report: RTX 4070 Ti 12 GB ran the sm_61 release zip, needed `f32` cuBLAS above 140 frames (now automatic on compute capability 7.0+) [user-reported, issue #1; `docs/OLCUMLER.md` §8] | Collect reports through the hardware-test issue template; try 6 GB cards |
| Re-verify the release binary | Measured numbers come from development builds (`docs/OLCUMLER.md`, section 0); the release binary is a fresh build | 56-frame byte gate passed for the release binary [measured]; 209-frame run through `uret.ps1` passed the gate [measured: U209]; latent byte-identical to the development-build run, frames and audio identical, file sha differs (container) [measured] | Only the 141-frame latent chain is not repeated with the release binary [not tried] |
| RTX 50 series (sm_120) | A contributor reported black video with the release engine and the v0.1.0 script; a native sm_120 build passed up to 209 frames | [user-reported, PR #3]; release engine with the v0.1.1 `f32` setting not tested | One 56-frame run of the release engine with the v0.1.1 script on an RTX 50 card; if it is still black, try the stock stable-diffusion.cpp CUDA release `master-1106-532d2c1` (its build file lists sm_120 [read]; not tried) before shipping our own sm_120 zip |
| Multi-architecture release build | The first release targets Pascal (sm_61) | Pascal build [measured]; others [guess] | The stock stable-diffusion.cpp CUDA release `master-1106-532d2c1` already lists sm_61 to sm_120 [read: build.yml], and an RTX 3070 report ran it without our patches [user-reported, PR #6]; so a multi-architecture zip of ours is only worth it for the memory patches. Decide after one more outside report; keep sha256 for any package |
| Upstream | Patches that are not experimental could help stable-diffusion.cpp users | Upstream PR #2369 (VAE encode padding) is already part of the base [read] | Prepare small, separately tested patches for upstream review; keep experimental ones out |
| Root cause of the black video on newer cards | `f32` fixes it, but the same variable also switches off a bf16 fused kernel on 8.x cards, so the cause is not isolated | Fix [user-reported, issue #1]; two candidates [read: engine `bf16.cu`, `common.cuh`] | Ask for a 141-frame run with only `GGML_CUDA_DISABLE_FUSION=1`; if that alone fixes it, report upstream |
| `-EndImg` (first-last frame) beyond what we measured | The end frame adds conditioning; on 4 GB the cap is 175 and two processes are forced | 56 and 175 frames passed, 192 and single-process did not fit [measured, GTX 1050 Ti, 2026-11-20]; 141 frames on 12 GB [user-reported, issue #1] | Try `-EndImg` without `-InitImg`; collect FLF reports from 6 GB and 8 GB+ cards before changing their cap or process rule |
| `-W`/`-H` on 4 GB | v0.1.1 accepts other sizes (multiples of 32, area at least 640x384); on cards under 8 GB a non-default size above the largest measured job (14880 tokens) is refused unless `VT_MAX_JETON` is set | Not tried on 4 GB; 12 GB report up to 720x1280 [user-reported, issue #1] | Measure one vertical size (384x640) on 4 GB; add a size table per card class |
| Quality gates at other sizes | Thresholds are calibrated at 640x384; at larger sizes raw noise reads lower | Same clip (F209V2) at 1280x768: noise 0.32 instead of 1.08, N 0.020 instead of 0.048 [measured: team test 2026-11-20, the F209V2 clip rescaled; evidence kept by the authors, not in this repo] | Calibrate per size or normalise to 640x384 before measuring |
| Single process on large cards | Two processes cost an extra model load; a 12 GB card ran 141 frames in one | `-TekAsama` manual switch only [user-reported, issue #1]; automatic choice by VRAM not taken (we cannot test it) | Collect large-card reports; decide on an automatic rule only with measurements |
| 22-frame "workspace capacity check" error | Reported once with a landscape init image | One run, no log [user-reported, issue #1] | Reproduce with `SD_CAPACITY_LOG=1` and the reporter's log |
| Clean-folder install test | The README does not claim "works" until it is seen | Pending | Run `scripts\kur.ps1` then `scripts\uret.ps1` in an empty folder, record log, hashes and time |
